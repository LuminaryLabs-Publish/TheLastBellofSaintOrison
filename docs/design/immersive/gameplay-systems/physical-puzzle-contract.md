# Physical Puzzle Contract

**Target specification; runtime implementation pending.**

Investigation should own a versioned mechanism record with explicit allowed controls, stable detents, prerequisites, current logical state and completion. The current installed puzzle service supports indexed answer sequences; it does not implement arbitrary analog mechanisms. Extending that contract is a named prerequisite, not a claim of existing support.

Define each interaction as input → validated transition → owner receipt → projected response. A blocked transition returns a reason with no unrelated mutation. A local control reset leaves verified knowledge and inventory intact. A completed mechanism cannot award rewards twice.

Long motion is presentation of the committed transition. If a moving object must remain interruptible before commitment, store an explicit logical pending action with cancellation; do not derive success from animation time or GPU state. Define what happens on pause, focus loss, scene exit and restore.

Finite sequences wait for operation receipts and choose the next authored activity. They do not own pressure, unrestricted JavaScript callbacks or a replacement scheduler. A future implementation must prove cancellation and restore against the pinned Nexus contract before migrating all rooms.
